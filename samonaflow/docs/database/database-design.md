# samonaFlow Database Design

Source of truth: `prisma/schema.prisma`. This document describes that file. Where the schema comments and the PRD (README.md, Section 8 and Section 10) differ, the schema is authoritative for structure and the PRD for business rules.

## 1. Architecture

- Database: PostgreSQL, hosted on Supabase.
- ORM: Prisma 7 using `@prisma/adapter-pg`. The adapter is a runtime setting and is not declared in the schema.
- Schema file: `prisma/schema.prisma`. Generator output is `../src/generated/prisma`.
- The `datasource db` block declares `provider = "postgresql"` only. No connection URL is in the schema.
- Money and business dates are typed in the schema as described in Section 6.

## 2. Entities

Enums: `BusinessRole` (OWNER, STAFF), `InvoiceStatus` (DRAFT, SENT, PARTIALLY_PAID, PAID, OVERDUE, VOID), `PaymentMethod` (UPI, BANK_TRANSFER, CASH, OTHER), `ExpenseCategory` (RENT, INTERNET, SOFTWARE_SUBSCRIPTIONS, SALARIES, EQUIPMENT, MARKETING, TRAVEL, UTILITIES, OTHER), `ExpenseStatus` (UPCOMING, OVERDUE, PAID, CANCELLED), `ReminderType` (UPCOMING_PAYMENT, DUE_TODAY, OVERDUE_PAYMENT, FINAL_FOLLOW_UP), `ReminderStatus` (DRAFTED, WHATSAPP_OPENED, MARKED_SENT), `AlertType` (OVERDUE_PAYMENT, PAYMENT_APPROACHING, POTENTIAL_SHORTAGE, UPCOMING_EXPENSE, PARTIAL_PAYMENT_DUE, CUSTOMER_CONCENTRATION), `AlertSeverity` (INFO, WARNING, CRITICAL).

- **UserProfile** (`user_profiles`): the application's user record. `id` is the Supabase Auth user UUID and is never generated by Prisma. Holds `email` (unique), `fullName`, and timestamps. No password or credential fields.
- **Business** (`businesses`): one tenant. Holds the owner reference (`ownerId`), name, owner name, contact fields, `businessType`, `currency` (default `INR`, CHAR(3)), `timezone` (default `Asia/Kolkata`), and `openingBalance` with `openingBalanceDate`. Business settings are fields on this model; there is no separate settings model.
- **BusinessMembership** (`business_memberships`): links a user to a business with a `role`. One row per user per business (unique `userId, businessId`).
- **Customer** (`customers`): a business's customer. Holds contact fields, optional `companyName`, `address`, `notes`, and `archivedAt`. Customers are archived, not deleted.
- **Invoice** (`invoices`): a bill to one customer. Holds `invoiceNumber` (unique per business), `issueDate`, `dueDate`, optional `expectedPaymentDate`, `status`, the amount fields `subtotal`, `discount`, `tax`, `totalAmount`, the `currency` snapshot, `notes`, and the public-link fields `publicTokenHash` and `publicTokenRevokedAt`.
- **InvoiceItem** (`invoice_items`): a line on an invoice. Holds `description`, `quantity` (Decimal(10,2)), `unitPrice`, `lineTotal`, and `position` (unique per invoice). `businessId` is carried so the composite FK can enforce tenancy.
- **Payment** (`payments`): money received against one invoice. Holds `amount`, `paymentDate`, `method`, optional `transactionReference` and `notes`. Has no `updatedAt`; payments are append-only.
- **PaymentReversal** (`payment_reversals`): the voiding record for a payment. Holds `reason`, `reversedById` (the user who reversed it), and `reversedAt`. At most one per payment (unique `paymentId`). Append-only; no `updatedAt`.
- **Expense** (`expenses`): a business outgoing with `title`, `category`, `amount`, `dueDate`, optional `paymentDate`, `status` (default UPCOMING), and `notes`. Not linked to customers or invoices.
- **Reminder** (`reminders`): a drafted payment reminder for one invoice and its customer. Holds `reminderType`, `status` (default DRAFTED), `message`, and optional `followUpDate`. Opening WhatsApp is not delivery; only MARKED_SENT is set by the user.
- **Alert** (`alerts`): a generated notification. Holds `alertType`, `severity`, `title`, `description`, a polymorphic `entityType`/`entityId` (no foreign key), an optional `dedupeKey`, read and resolved timestamps.

## 3. Relationships and foreign keys

Simple foreign keys:
- `Business.ownerId` -> `UserProfile.id` (Restrict)
- `BusinessMembership.userId` -> `UserProfile.id` (Cascade)
- `BusinessMembership.businessId` -> `Business.id` (Cascade)
- `Customer.businessId` -> `Business.id` (Restrict)
- `Expense.businessId` -> `Business.id` (Restrict)
- `Alert.businessId` -> `Business.id` (Restrict)
- `Invoice.businessId` -> `Business.id` (Restrict)
- `InvoiceItem.businessId` -> `Business.id` (Restrict)
- `Payment.businessId` -> `Business.id` (Restrict)
- `PaymentReversal.businessId` -> `Business.id` (Restrict)
- `PaymentReversal.reversedById` -> `UserProfile.id` (Restrict)
- `Reminder.businessId` -> `Business.id` (Restrict)

Composite foreign keys (tenant consistency):
- `Invoice (customerId, businessId)` -> `Customer (id, businessId)`: the invoice's customer must belong to the invoice's business.
- `InvoiceItem (invoiceId, businessId)` -> `Invoice (id, businessId)` (Cascade): items are removed with their invoice and must match its business.
- `Payment (invoiceId, businessId)` -> `Invoice (id, businessId)` (Restrict).
- `PaymentReversal (paymentId, businessId)` -> `Payment (id, businessId)` (Restrict).
- `Reminder (customerId, businessId)` -> `Customer (id, businessId)` (Restrict).
- `Reminder (invoiceId, customerId, businessId)` -> `Invoice (id, customerId, businessId)` (Restrict). This is the key rule for reminders: a reminder's customer must equal the customer of the invoice it references, and both must belong to the same business. The database rejects any other combination.

Targets of these composite keys are declared as `@@unique`: `Customer (id, businessId)`, `Invoice (id, businessId)`, `Invoice (id, customerId, businessId)`, `Payment (id, businessId)`.

## 4. Multi-tenancy and access

- Every business-owned row carries `businessId`. Child rows that must match their parent's business use composite foreign keys (Section 3).
- Users reach a business only through `BusinessMembership`. `Business.ownerId` identifies the owner; the owner's membership row is the access record (see Section 9).
- Supabase Auth owns identity. `UserProfile.id` is the Supabase Auth UUID. Rows are created at signup to mirror `auth.users`.
- Prisma connects as the database role, which bypasses Row Level Security (RLS). Isolation is therefore enforced in the service layer: every query is scoped to a `businessId` taken from a verified membership.
- RLS is planned later as defense in depth. For pooled connections, RLS policies will need JWT claims set per transaction with `set_config`.

## 5. Currency

- `Business.currency` defaults to `INR` (ISO 4217, CHAR(3)).
- `Invoice.currency` is a snapshot copied from the business when the invoice is created. It is not a live link.
- The issued invoice currency must not change. The service rejects changes once an invoice leaves DRAFT. A database trigger to enforce this is listed in `docs/database/pending-constraints.sql`.
- Payments are recorded in the invoice's currency. `Payment` has no currency column.

## 6. Financial handling

- Money is `Decimal(12,2)`. Quantities are `Decimal(10,2)`. Floats are not used for any money or quantity field.
- Outstanding amount is derived, not stored: `totalAmount - (sum of payments - sum of reversed payment amounts)`.
- `Invoice.subtotal`, `discount`, `tax`, and `totalAmount` are stored values that record the issued document. They are not recalculated from items after issue.
- Invoice status: DRAFT, SENT, PARTIALLY_PAID, PAID, and VOID are set by the service. The transition rules are in PRD FR-04.
- OVERDUE is derived from `dueDate` using the business-local date (`Business.timezone`). The `status` value is a cache that the service refreshes; it is not the source of truth.
- Business dates (`issueDate`, `dueDate`, `paymentDate`, `openingBalanceDate`, `followUpDate`) are `DATE`, interpreted in the business's timezone. Event times (`createdAt`, `updatedAt`, `reversedAt`, `archivedAt`, etc.) are `timestamptz(6)`.

## 7. Payment voiding and reversal

- Payments are never edited or deleted. The schema has no update or delete path for payments; `Payment` has no `updatedAt`.
- Voiding a payment creates one `PaymentReversal` row with `reason`, `reversedById`, and `reversedAt`. The unique `paymentId` allows at most one reversal per payment.
- The original payment and its reversal together form the audit trail.
- The outstanding formula in Section 6 counts a reversed payment as if it did not happen.

## 8. Deletion rules

- `Restrict` on all financial references: invoices, payments, reversals, reminders, and the business and user links that they depend on cannot be deleted while referenced.
- `Cascade` only for:
  - `InvoiceItem` from `Invoice`.
  - `BusinessMembership` from `UserProfile` and from `Business`.
- Customers are archived with `archivedAt`, not deleted.

## 9. Owner membership consistency (document only)

Not enforced by the schema. Enforce in the service during onboarding:
- When a Business is created, the same transaction must create a `BusinessMembership` with role `OWNER` for that `businessId` and `ownerId`.
- `Business.ownerId` must have a matching OWNER membership at all times.
- Services must not allow removing that membership.

A database constraint is not used because it needs cross-row logic. See the migration TODO list in `pending-constraints.sql`.

## 10. Not stored

- Forecasts and what-if scenarios. They are derived or temporary, per the PRD.
- Payment allocation. There is no allocation table: each payment applies to exactly one invoice (PRD FR-05).
- Public invoice links store only `publicTokenHash` (SHA-256 hex digest of a random token, never the raw token) and `publicTokenRevokedAt`.

## 11. Indexes

Unique constraints and primary keys are listed where they also serve as indexes or FK targets.

**user_profiles**
- `email` unique: login lookup and duplicate prevention.

**businesses**
- `(ownerId)`: list businesses owned by a user; supports the `Business.ownerId` foreign key.

**business_memberships**
- `(userId, businessId)` unique: access check for a user in a business.
- `(businessId)`: list members of a business. This is the one child-table businessId-only index in the schema (see note below).

**customers**
- `(id, businessId)` unique: target of composite FKs.
- `(businessId, archivedAt)`: active versus archived customer lists.
- `(businessId, name)`: customer list sorted and searched by name.

**invoices**
- `(businessId, invoiceNumber)` unique: invoice number per business.
- `(id, businessId)` unique: target of the InvoiceItem and Payment composite FKs.
- `(id, customerId, businessId)` unique: target of the Reminder composite FK.
- `publicTokenHash` unique: public link lookup by token hash.
- `(businessId, status)`: invoice lists filtered by status.
- `(businessId, dueDate)`: overdue and upcoming invoice queries.
- `(customerId)`: a customer's invoices; supports the `Invoice.customerId` foreign key.

**invoice_items**
- `(invoiceId, position)` unique: line order within an invoice.
- `(invoiceId)`: items of an invoice. This is a prefix of the unique index above, so it is largely redundant; it is kept as the schema defines it.

**payments**
- `(id, businessId)` unique: target of the PaymentReversal composite FK.
- `(invoiceId)`: payments for an invoice; supports the invoice foreign key.
- `(businessId, paymentDate)`: payments in a date range for dashboard history.

**payment_reversals**
- `(paymentId)` unique: at most one reversal per payment.

**expenses**
- `(businessId, status, dueDate)`: upcoming and overdue expenses.

**reminders**
- `(invoiceId)`: reminders for an invoice.
- `(customerId)`: reminders for a customer; supports the `Reminder.customerId` foreign key.
- `(businessId, followUpDate)`: follow-up reminders due by date.

**alerts**
- `(businessId, resolvedAt)`: active (unresolved) alerts.
- `(businessId, dedupeKey)`: dedupe lookup before creating an alert.

Note: businessId-only indexes were deliberately not added on child tables (for example `invoices`, `payments`, `customers`, `expenses`). Business-scoped queries are covered by the composite indexes above, which lead with `businessId`. `business_memberships` is the exception shown above.

## 12. Assumptions

- `UserProfile` rows are created at signup and mirror `auth.users`.
- The service refreshes the cached OVERDUE status.
- `STAFF` is reserved in `BusinessRole`. Only `OWNER` is used in the MVP.

## 13. Open questions

- Whether one user may own several businesses. The schema allows it (`Business.ownerId` is not unique); PRD FR-01 is silent.
- Whether a payment reversal may itself be undone. The schema does not allow it.
- Whether a reversed payment still counts in dashboard history. The schema keeps both rows, so either choice is possible in queries.
